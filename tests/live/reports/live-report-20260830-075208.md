## Where the time went

A single blended latency number cannot tell you whether **our framework** or **the model** got slower — swap provider and it moves for reasons that have nothing to do with our code. So each phase is attributed to whoever spent it.

| Phase | Owner | Total | Share | What it is |
|---|---|---:|---:|---|
| setup | **ours** | 260 ms | 1.14% | build model object, compose instructions, resolve tools, construct agent |
| wait | provider | 13739 ms | 60.37% | request sent → first token: network round trip, provider queue, input prefill |
| stream | provider | 418 ms | 1.84% | first token → last token: decode, scales with output tokens |
| finalize | **ours** | 0 ms | 0.00% | read usage, walk messages, build result |

**Framework total: 260 ms (1.14%). Model total: 14157 ms (98.86%).**

Decode throughput: **2438 tokens/sec** (1019 output tokens in 418 ms of decode). Measured on stream time only, so provider queueing does not dilute it.

**Read this as: the framework is not the bottleneck.** At 1.14% of wall clock, optimising Pikachu's own code cannot meaningfully change turn latency. The levers that matter are the model, the provider/region, and the size of the prompt and requested output.

`wait` is 32.9× `stream`, so this turn spent far longer **waiting** for the provider than **receiving** from it. Waiting is provider queue and network, not model speed — a faster model would not help; a less contended provider or region would.


## Prompt caching — the open question

**Caching did NOT fire.** `cache_read_tokens` is 0 across every task.

Two candidate causes, and they need different responses:

1. **The prefix is below the model's floor.** Our stable prefix is ~1,500–2,400 tokens and Gemini's blanket documented minimum is 4,096. If this is the cause, caching is enabled and doing nothing, and S1 is unreachable on this model.
2. **The counter is not reported.** Google's implicit caching returns 0 for cache reads through some paths even when it fired ([pydantic-ai #5205](https://github.com/pydantic/pydantic-ai/issues/5205)). Confirm against the OpenTelemetry span before concluding cause 1.

Note these test prompts are short — well under the prefix size a real turn carries — so a 0 here is **expected** and is not yet evidence about the floor. The floor question needs a turn with a full skill body and tool schemas loaded.

`CACHE_FLOOR_UNVERIFIED` remains `True`.
